# v1.1.2 profile rollout: integration checklist

Status: **NOT READY FOR CUSTOMER APK TEST**. DeviceLocalProfilesFeature.ENABLED remains false. The authenticated mode provider now also explicitly refuses customer-local activation even if a single-remap journal says COMPLETED; this is intentional until a verified account-wide migration certificate and full sync isolation exist.

## Required account behavior

- Family account: Main and family-created profiles are remote-backed and follow the same login on all devices; personal viewing state follows each family profile.
- Shared customer account: Main controls addons, plugins, catalog and row layout. Up to five personal profiles per device stay private to that device. Personal history, progress, watchlist and profile metadata must never be uploaded under the shared account.
- Never decide mode from profile name or profile ID. Resolve from verified authenticated account identity. Missing or changed identity defaults to legacy cloud behavior.

## Blocking integration work

1. Persist the verified account-mode assignment keyed by stable authenticated account ID; clear/ignore stale assignment on logout/account switch. Wire AccountProfileModeResolver into the actual authentication lifecycle.
2. Replace global DeviceLocalProfilesFeature.ENABLED checks in sync services and stores with a per-account resolved mode. Family mode must preserve all legacy sync paths.
3. Implement a non-destructive customer migration transaction: back up existing local profiles and state, map colliding secondary IDs without losing viewing data, persist completion, and avoid remote profile deletion.
4. Ensure shared Main layout and plugin/addon configuration are refreshed on secondary profiles without importing Main's personal viewing state. Test cross-device changes while a secondary is active.
5. Audit and test all upload, download, realtime and background sync paths (including Trakt, collections, provider credentials, watch history, progress, PIN, and profile settings). Customer personal state must never reach the shared account. See `docs/v1.1.2-personal-state-sync-audit.md`: initial permission checks do **not** protect against account or mode switches while requests are suspended; response application and mutation acknowledgments also require identity checks.
6. Run unit and instrumentation tests plus signed install-over upgrade verification on production v1.1.1. Test family and customer accounts separately and verify logout/account switching.
7. Only after checks pass, produce an isolated beta APK for user testing. Do not publish to production store or change v1.1.1.

## Safety controls already added

AccountProfilePolicy, AccountProfileModeCodec, AccountProfileModeResolver, AccountProfileTransitionPolicy, DeviceProfileMigrationPlanner and CustomerProfileMigrationGate provide testable policy/preflight boundaries. These are **not yet wired to login and migration execution**. A passing Android build does not prove privacy isolation.

The profile migration copy, backup inventory, recovery checks and metadata checkpoints are copy-only or gated operations. ProfileDataStoreFactory.prepareProfileRemap now takes an in-process source/target access barrier before previewing the complete primary-and-shadow-backup manifest; its returned preparation must be closed after use. The opt-in `withGuardedProfileRemap` helper keeps this barrier in place across suspending migration work, checks the verified account before and after the operation, and releases the barrier even on failure or cancellation. **Neither helper authorizes migration by itself or runs on startup.** A complete executor still must stop existing DataStore references, background/realtime sync and shadow writers, check verified account identity throughout, coordinate OS file locks, handle crashes and multiple profile collisions, and prove privacy isolation before rollout. The single-remap COMPLETED journal must not be treated as proof that all account profiles were migrated.

## Release-critical execution order (do not substitute more isolated copy tests)

1. **Inventory actual stores and writers.** Trace the runtime profile DataStore factory and every file it opens, plus Room/SharedPreferences, watch progress, watched items, watchlists, PINs, credentials, Trakt and collections. Build an exhaustive, versioned manifest for each profile; account for live DataStore references and shadow backups.
2. **Quiesce writes and sync.** Coordinate authentication transitions, profile selection, all DataStore writers, background jobs and realtime subscriptions under a shared transition barrier. Cancel old-account work before copying.
3. **Migrate as one account-bound transaction.** Persist an account-wide manifest with source and destination hashes, all profile-ID remaps and verified account identity; journal each step durably. Never delete sources or overwrite destinations. On crash, require deterministic inspection/reconciliation and refuse activation until complete.
4. **Prove customer isolation.** Test same-login devices with different local history, account switching during suspended RPCs, logout, shared Main layout updates, and family account sync unchanged. Audit every outbound personal-state RPC and inbound merge.
5. **Validate install-over.** Build and sign isolated 1.1.2 beta, install over actual 1.1.1 on Fire TV and Onn, verify login/addons/watch state retained, then obtain explicit go/no-go before any rollout.

**Current limitation:** The new multi-file batch copier and read-only recovery inspector are development primitives, not a migration executor. The single-remap journal has no exhaustive account-wide manifest. Passing ABI/unit CI alone does not satisfy any of steps 1–5. Do not re-enable customer-local mode merely because a single journal reaches COMPLETED.
